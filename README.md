# Decision Diff

Система анализа изменений стратегии СПР (модули 3 и 4): приводит два среза ответов СПР — BEFORE (MASTER) и
AFTER (BETA) — к вертикальной витрине, сравнивает их, исполняет пользовательские процедуры и автопроверки и
показывает в браузере отчёт: вердикт, куда сместились решения, кластеры изменений «логика или входные данные»,
сводную таблицу с изменяемой раскладкой и переход от любого числа до заявки и атрибута.

## Быстрый старт (чистая машина, нужен только Docker)

Требования: 64-битная Linux, macOS или Windows 10/11, 4 ядра и 8 ГБ памяти (воркеру выделено до 4 ГБ), 5 ГБ на диске
плюс место под датасеты, доступ в интернет для первой сборки.

### 1. Установите Docker и git

**Linux (Ubuntu, Debian, Fedora и др.)** — официальный скрипт ставит Docker Engine и плагин Compose:

```bash
sudo apt-get update && sudo apt-get install -y git curl   # Fedora: sudo dnf install -y git curl
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker            # docker без sudo в текущей сессии
```

**macOS** — установите [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/) (Apple Silicon или
Intel), запустите его и дождитесь статуса "Engine running". git ставится командой `xcode-select --install`.

**Windows 10/11** — установите [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) с
бэкендом WSL 2 (установщик предложит включить WSL) и [Git for Windows](https://git-scm.com/download/win). Команды ниже
выполняйте в терминале WSL (Ubuntu) или в Git Bash.

Проверьте, что всё на месте (нужен Compose v2: команда `docker compose`, а не `docker-compose`):

```bash
docker --version && docker compose version && git --version
docker run --rm hello-world
```

### 2. Поднимите приложение

```bash
git clone https://github.com/bigbruh-mephi/decision-diff.git && cd decision-diff
cp .env.example .env            # задайте пароли DD_ADMIN_PASSWORD, DD_PG_PASSWORD, DD_AMQP_PASSWORD
mkdir -p datasets && cp -r /путь/к/RUN-20260827-0001 datasets/
docker compose up -d --build    # первая сборка 3-10 минут, дальше секунды
docker compose ps               # api, worker, postgres, rabbitmq: running / healthy
```

Без паролей в `.env` compose остановится с подсказкой, какую переменную задать. Остановить: `docker compose down`
(данные сохраняются в томах; `down -v` удалит их). Обновить после `git pull`: `docker compose up -d --build`.

Откройте http://localhost:8080 и войдите как `admin` с паролем `DD_ADMIN_PASSWORD` из `.env`. Остальные пользователи
регистрируются на странице входа (`DD_OPEN_REGISTRATION=1`; в общей сети поставьте `0`). По адресу машины в сети
приложение тоже работает, но без HTTPS сессия передаётся открыто.

**Пользователи.** Регистрация по умолчанию закрыта. Для демонстрации или команды аналитиков поставьте
`DD_OPEN_REGISTRATION=1` в `.env` и перезапустите `api`: каждый зарегистрируется на странице входа
("Зарегистрироваться"), прогоны и рабочие области у всех свои. После этого флаг можно вернуть в `0`.

**Датасет** — папка прогона модуля 2: `manifest.json` (необязательно) и `RESULTS/BEFORE*/`, `RESULTS/AFTER*/`, где имя
файла — идентификатор заявки. Папки из `datasets/` видны в форме «Новый прогон»; архив `.zip` можно загрузить прямо из
интерфейса. Каталог задаётся переменной `DD_DATASETS_PATH`.

**Процедуры и проверки** — файлы `.py` в `procedures/` (подключаются как «размещённые в системе»). Выданные
организаторами проверки положите в `procedures/checks/` — они исполняются без изменений:

```bash
cp /путь/к/пакету/checks/check_*.py procedures/checks/ && docker compose restart api
```

Свои процедуры и проверки можно писать в «Рабочей области» приложения.

## Как пользоваться (сценарий демонстрации)

1. **Конфигурации** → "Новая конфигурация" (пустая) или "Из готовой: СПР кредиты" → список шагов сверху вниз:
   разбор формата, подготовка документов, приведение, сравнение, разрезы, цепочка этапов, автопроверки, промпт ИИ.
   У каждого шага описание бизнес-смысла, "код" открывает его в редакторе, "+ Добавить шаг" - готовый шаг или новый
   из шаблона. "Запустить ▶" → **Новый прогон**: папка прогона (BEFORE и AFTER) или два датасета, конфигурация,
   "Запустить". Флаг "принимать догрузку порций" оставляет прогон открытым для новых пачек ответов.
2. **Журнал этапов** — во время обработки: этапы, время, строки, события в реальном времени (SSE, переживает
   перезагрузку). "код …" открывает ту версию процедуры, которая исполнялась.
3. **Обзор** — вердикт (с различиями, смена исхода, доля положительных исходов), сводка автопроверок, матрица
   переходов, кластеры изменений с одной причиной смены исхода на объект (порог, целевая модель, стоп-факторы).
4. **Сводная таблица** — поля перетаскиваются или добавляются кликом; значения "было/стало" рядом; число или доля от
   строки, колонки, всего; готовые и свои шаблоны раскладки (сохранить, поделиться); точное число различных объектов.
5. **Провал до данных**: клик по числу → список объектов (с подписью, что именно открыто) → объект: документ до и после
   построчно с подсветкой изменений → атрибут.
6. **Автопроверки** — все строки всех проверок одной таблицей, FAIL с низкой уверенностью — бледные; «N шт.» ведёт к
   заявкам.
7. **Новая проверка** → рабочая область: ячейки `# %%`, выполнение в песочнице на данных прогона, «Применить к прогону»
   — строки появляются в том же отчёте.
8. **Скачать HTML** — самодостаточный файл; ссылки из него ведут в интерактивный отчёт. «Ссылка на отчёт» —
   отзываемая ссылка только для чтения.

## Архитектура

```
браузер ── HTTPS ── api (FastAPI) ──┬── PostgreSQL 18: пользователи, конфигурации, прогоны, порции, журнал, события,
   (SSE прогресс)      │            │                  проверки, версии кода (источник правды)
                       │            └── run.duckdb: неизменяемый файл прогона (витрина, факты, битмапы, кластеры)
                       └── RabbitMQ 4 (quorum, DLQ, retry) ── worker × N ── песочница на каждое исполнение кода
```

- **Приём**: пачка ответов режется на порции и каждая порция сразу уходит в очередь; ответы могут приходить
  несколькими пачками, обработка не ждёт конца прогона.
- **Порция** (в песочнице): формат → дерево (JSON/NDJSON/XML/YAML/CSV/MessagePack/архивы) → нормализация (ключи
  массивов по шаблонам путей, исключения, бакеты, переименования) → сравнение (4 типа изменений, по VALUE) → разрезы →
  Parquet.
- **Сборка** (ровно один раз через условный переход состояния в PostgreSQL): DuckDB-файл, отсортированный по
  `(path_id, ARRAY_KEY, app_ord, SOURCE)`, факты counts с roaring-битмапами заявок, кластеры изменений, переходы
  значений; затем проверки (каждая в своей песочнице) и альтернативное мнение ИИ.
- **Отчёт**: все числа — точные количества различных заявок (битмапы), срез (scope) в URL, ответы кешируются с ETag.
- **Глубина вложенности** ограничена только парсером: JSON (orjson) и MessagePack 1024 уровня, XML (lxml) 2048, YAML (PyYAML) около 500; глубже — понятная ошибка с указанием предела, без обрезки.
- **Пользовательский код** (процедуры, проверки, ячейки) исполняется только в воркере: fork из однопоточного процесса,
  отдельный uid, rlimits, no_new_privs, Landlock (только чтение витрины, запись в одну папку, без сети), seccomp,
  пустое окружение, результат только JSON. API пользовательский код не исполняет.

Код приложения не знает имён полей датасета: всё доменное — в `procedures/` (профиль нормализации, правила
сравнения, разрезы, проверки) и меняется без изменения кода.

## Контракты процедур

Платформа не привязана к предметной области: кредиты - только поставляемая демонстрационная конфигурация. Конфигурация -
это список шагов сверху вниз (разбор формата, подготовка документов, приведение, сравнение, разрезы, цепочка этапов,
автопроверки, промпт ИИ); каждый шаг - процедура на Python, которую владелец конфигурации правит прямо в приложении.
Поставляемый файл не меняется: правка сохраняется как своя версия и используется в следующих прогонах, а каждый прогон
запоминает версию кода, которая исполнялась.

Модуль экспортирует `PROCEDURE` (или `CHECK` для проверок) — `{"id", "label", "kind", "description", "params",
"entrypoint"}`; `description` - бизнес-смысл шага простыми словами, его видно в конфигурации.

| kind | params | entrypoint |
|---|---|---|
| `parser` | любые | `(name, data: bytes, params) -> [(id объекта, документ)]` - свой формат или протокол; без него автоопределение JSON/NDJSON/XML/YAML/CSV/MessagePack/Parquet/архивов |
| `step` | любые | `(doc, params) -> doc` - подготовка документов, шаги по порядку до приведения |
| `normalize` | `arrays` (шаблон пути → `["поле", ...]` / `"@value"` / `"@index"`), `exclude`, `buckets`, `rename`, `key_style`, `xml_array_tags`, `id_field` | необязательно `(doc, params) -> doc` |
| `compare` | `equivalent`: `[{"pattern", "values": [[a, b]]}]` | — |
| `segments` | `multi_valued`, `decision_field`, `positive_decision`, `input_paths`, `pii_paths` | `(before, after, params) -> dict` |
| `check` | любые | `(mart, params) -> [строки PASS/FAIL]` (контракт выданных проверок) |
| `ai_prompt` | `system`, `call1`, `call2` - тексты промпта ИИ с плейсхолдерами `{pack}`, `{schema}`, `{derived}`... | - (текст, не исполняется) |
| `whatif` | входы и факторы модели решения | `(data, params) -> исход на объект`; по ней система находит причину каждой смены решения |

Шкалы бакетов (`buckets` в `normalize`) задает пользователь по шаблону пути: у разных атрибутов и даже у одного
атрибута в разных скоркартах они разные (0-1 и 1-1000), поэтому общей шкалы нет. Для сложных правил - свой шаг
`step` или `entrypoint` нормализации.

`mart`: `rows(**filters)`, `count(**filters)`, `app_ids(**filters)`, `segments()`, `total_apps()`.

## Альтернативное мнение ИИ

Любой OpenAI-совместимый endpoint: `DD_LLM_BASE_URL`, `DD_LLM_API_KEY`, `DD_LLM_MODEL` в `.env`. Тексты промпта -
шаг конфигурации `ai_prompt`: их можно переписать под свою предметную область прямо в приложении. Два вызова: модель
предлагает гипотезы с производными признаками (SQL-выражения проверяются по белому списку и вычисляются по всем
заявкам), затем пишет выводы, где числа подставляются из измерений. ИИ - второй аналитик, а не источник истины:
сначала показываются выводы, подтвержденные измерениями, затем гипотезы модели без подтверждения - бледно и с
причиной. Без настроек блок выключен, остальное работает.

Проверено на реальных моделях через Groq, открытый прогон 2 002 заявки, около 14 с и меньше цента на мнение:
`openai/gpt-oss-20b` дает гипотезы первого порядка и слабые формулировки; `openai/gpt-oss-120b` пишет по-русски,
соблюдает формат и находит связи "над атрибутами" (например, постоянный сдвиг скора на -140 ровно у заявок
кластера "из-за входных данных"). Для демо рекомендуется `DD_LLM_MODEL=openai/gpt-oss-120b`.

## Замеры (ноутбук i5-12450H, 12 потоков; открытый прогон 2 002 заявки, весь путь через брокер и песочницу)

| Что | Планка «отлично» | Замер |
|---|---|---|
| Приведение + сравнение + сборка + проверки | ≤ 30 с | 1,8–2,9 с (20 020 заявок: ~10 с) |
| Открытие отчёта | ≤ 0,5 с | 35–45 мс |
| Повторное открытие | мгновенно | 3–5 мс, 304 по ETag |
| Смена раскладки сводной / фильтр | ≤ 0,3 с | 5–10 мс |
| Переход к заявкам / к заявке | ≤ 0,3 с | 4–7 мс / 13–17 мс |

Синтетический прогон ×50 (100 100 заявок, 28,6 млн строк витрины), тот же стек: весь прогон 83,5 с; открытие
отчёта 70 мс (повторно 2,5 мс); сводная 4–7 мс; провал к заявкам 6 мс, к заявке 33 мс.

`kill -9` воркера посреди прогона: после перезапуска прогон завершается с теми же числами, без дублей.

## Разработка

```bash
uv sync                                   # Python 3.12, зависимости из uv.lock
docker compose up -d postgres rabbitmq
uv run dd-worker &                        # воркер
uv run uvicorn decision_diff.api:app --port 8765
cd src/web && npm ci && npm run dev       # фронтенд с прокси на API
uv run pytest -q && uv run ruff check src tests procedures
DD_LIVE_URL=http://localhost:8080 DD_LIVE_LOGIN=admin DD_LIVE_PASSWORD=... uv run pytest tests/test_api_live.py
```

Сквозной тест `tests/test_api_live.py` создаёт прогон через HTTP API запущенного стека и проверяет отчёт, песочницу
и ссылки на отчёт. Документация API (`/api/docs`) включается `DD_API_DOCS=1`, метрики Prometheus (`/metrics`) —
заданием `DD_METRICS_TOKEN` (запрос с `Authorization: Bearer <токен>`).

`uv run dd submit <папка_прогона> --wait` — запуск прогона из командной строки.
